Kumiho · 九尾狐 · Graph-Native Memory

Your agent's memory shouldn't be a pile of chat logs.
It should be a knowledge graph that knows what it knows.

Kumiho Memory decomposes every conversation into a typed graph — entities, facts, decisions, events — at write time, and recalls with structure-aware retrieval that joins evidence across sessions the way a person connects memories. Fully open cognitive layer. Receipts in token-F1, the metric that can't be inflated.

The architecture — prospective indexing, event extraction, and formal AGM belief-revision semantics for versioned memory — was first described in Park, Graph-Native Cognitive Memory for AI Agents (arXiv:2603.17244, 2026). This page is that paper, running in production.

01How memory is written — conversation → typed graph

Every consolidation is a graph build by default (opt out with KUMIHO_MEMORY_ONTOLOGY=0). No batch jobs, no offline ETL — the graph exists the moment the conversation is saved.

Input: an ordinary conversation

User: We adopted a golden retriever last weekend — Caroline named him Max.
User: Also decided to go with Acme for pet insurance, their vet coverage is better.
Asst: Congrats! I'll remember Max, and that Acme covers his vet bills.

Step 1 — Consolidation: one LLM pass, strict structured output

Working memory (Redis) buffers turns; at the threshold, a single summarizer call emits a schema-enforced JSON — the same schema whether the ontology is on or off, so structured decomposition never perturbs the base summary:

{
  "summary": "Adopted a puppy named Max; chose Acme for pet insurance",
  "classification": { "entities": ["Caroline", "Max", "Acme"] },
  "knowledge": {
    "facts": [ {"claim": "Caroline adopted a puppy named Max", "certainty": "high"},
                {"claim": "Acme pet insurance covers Max's vet bills", "certainty": "high"} ],
    "decisions": [ {"decision": "Use Acme for pet insurance", "reason": "better vet coverage"} ],
    "actions": [], "open_questions": []
  },
  "events": [ {"event": "Adopted Max", "when": "last weekend", "participants": ["Caroline"]} ]
}

Step 2 — Materialization: every claim becomes an addressable node

Each typed node is a first-class versioned item with its own kref (Kumiho reference), its own revision history, and its own embedding. Re-learning the same fact stacks a revision instead of duplicating a node (get-or-create by identity slug):

Step 3 — Edges: provenance, aboutness, grounding, belief update

edgemeaninghow it's decided (deterministic — no LLM guessing)
DERIVED_FROMprovenance: every typed node → its source conversationalways, at materialization
ABOUT / INVOLVESfact/decision → entity · event participant → entitytoken-boundary mention match (no substring false-positives; Hangul-aware — "김" never matches "김치")

Index hygiene is part of the design: derived nodes are excluded from the lexical (BM25) corpus server-side — their text duplicates the conversations and would otherwise skew global IDF — while remaining fully reachable by kref traversal and vector search. Structure without pollution.

02How memory is recalled — retrieval that can do a JOIN

Query: “Where does the person who adopted Max work?” The two pieces of evidence live in different sessions and share almost no vocabulary. Flat vector search — everyone else's retrieval — has no mechanism to connect them. A typed graph does.

Reformulate LLM → angles

The question is decomposed into angles: “who adopted Max” · “Caroline's employer” — each angle is a separate probe into memory.

Parallel hybrid recall per angle BM25 + vector · per-angle cross-encoder

Each angle hits the server's fused lexical+semantic search; results merge by kref with angle attribution preserved. angle₁ top: adoption session (0.82) · angle₂ top: insurance session (0.61).

Entity-Bridge Join — the typed-graph JOIN

  • Both angles' hits point ABOUT the same entity → entities/max.entity is a bridge: the node that connects the question's sub-facts.
  • The bridge's terse fact nodes surface with a real inherited score = 0.9 × the weaker angle (0.9 × 0.61 = 0.549) — measured relevance by proxy, vouched for by both angles.
  • Hub entities (a speaker linked from everything) are deferred, not dropped — degree-aware so ubiquitous anchors can't flood the join, but 2-person corpora where the speaker IS the join key still work.

Fact-Recall leg — answer-shaped claims as first-class candidates

  • One semantic search of the facts space with the original question — atomic claims are the exact shape an answer needs (“Acme pet insurance covers Max's vet bills”), and dates ride inside claims for temporal questions.
  • Scored relative to the weakest conversation hit (axis-invariant) — a fact can add evidence but can never outrank or evict a conversation on any score scale.
  • Measured on a paired same-corpus A/B: +0.054 overall, every category up, 23 wins / 4 losses per question.

Structural traversal + entity 2-hop walk DERIVED_FROM · SUPERSEDES · score-less trail

Edges from top hits pull in provenance and superseding versions; a bounded entity walk adds same-entity siblings as trailing, reserve-slot context (never competing with scored hits).

Evidence-weighted rerank evidence level · recency · event-proximity · MMR

Deterministic priors — officially-graded memories, temporal proximity for date questions — applied once, idempotently, to scored entries only.

Additive context composition — augmentation that can't regress

The base top-K context is the exact head-slice flat recall would produce; bridge facts and typed claims are appended on top with their own budgets, never displacing it. With the ontology off, output is byte-identical to flat recall — structure is strictly additive, by construction.

The answering model reads F1 ⋈ F3 side by side and says “Acme” — the join is trivial once the two atomic claims are placed together. That placement is what the graph buys.

04Engineering principles

principlewhat it means in the code
Additive, never displacingGraph evidence rides on top of flat recall's exact output with its own slot budgets — turning the ontology on cannot make any answer worse by construction, and the paired 23W/4L measurement confirms it.
Byte-identical off-switchWith KUMIHO_MEMORY_ONTOLOGY=0, prompts, schemas, and recall output are byte-for-byte the legacy pipeline — asserted by tests, not by promise.
Deterministic edgesRelational edges come from token-boundary matching and overlap thresholds, not LLM guesses — reproducible graphs, no hallucinated links, no per-edge inference cost.
Everything is versionedFacts and decisions stack revisions like code: the current belief is the head, history is one hop back, SUPERSEDES records why.
Multilingual by designKorean-aware tokenization end to end — mention matching that respects Hangul boundaries, lexical search with ko-dic morphology.
Paired measurement cultureEvery retrieval change ships with a same-corpus paired A/B; single-run deltas don't count. The numbers above survived that bar.

05Open where it builds trust, closed where it's the moat

Open — the cognitive layer

pip install kumiho-memory

  • The full consolidation pipeline and structured-output schema
  • Ontology decomposition: typed nodes, spaces, all edge rules
  • The complete recall stack: reformulation, bridge join, fact leg, evidence rerank, additive compose
  • The benchmark harness — every number on this page is reproducible from source

Proprietary — the engine

Kumiho Server (local Community Edition & cloud)

  • Rust graph engine: krefs, revisions, edges, spaces over Neo4j
  • Hybrid search: per-leg normalized BM25+vector fusion, index-hygiene for derived kinds
  • Multi-tenancy, scoping guards, rate limiting, Korean morphological indexing

The split is deliberate: the layer that makes claims about how memory should think is open and auditable — run the harness, check the numbers. The engine that makes it fast, safe, and multi-tenant is the product.
