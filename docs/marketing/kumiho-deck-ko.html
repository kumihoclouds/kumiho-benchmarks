02

요약이 덱에서 다루는 것

Part 1 · 저장 (S05–S13)

대화가 어떤 형식으로 저장되는가 — 실제 리비전 metadata 원문, kref 주소 체계, 리비전 스태킹(한 아이템에 19개 리비전), 온톨로지 분해(한 대화 → 타입 노드 221개), 엣지 501개의 생성 규칙, 인덱스 위생.

Part 2 · 리콜 (S14–S19)

질문이 어떻게 답이 되는가 — 하이브리드 검색, 엔티티-브리지 조인(그래프 JOIN), fact-recall 레그, 증거 가중 재랭크, 추가-비대체 컨텍스트 조립.

Part 3 · 증거 (S20–S22)

실전 win 사례(오답→정답 전환의 원문 증거), 페어 A/B 측정 방법론, 경쟁사 F1 비교.

Part 4 · 기술/구조 (S23–S24)

기술 스택 상세, 오픈코어 경계 — 무엇이 열려 있고 무엇이 모트인가.

03

문제평면 메모리(로그 + 벡터)의 세 가지 실패 모드

① 멀티홉 — JOIN이 없다

"Max를 입양한 사람은 어디서 일해?" — 근거 두 개가 다른 세션에 있고 공통 어휘가 없으면 벡터 유사도는 둘을 연결할 방법 자체가 없다. 검색은 similarity지 join이 아니다.

② 시간 — 날짜는 임베딩에 안 실린다

"언제 프라이드 퍼레이드에 갔지?" — 날짜는 임베딩 공간에서 거의 구분되지 않는다. 시간 정보는 구조화된 필드로 뽑아둬야 랭킹에 쓸 수 있다.

③ 신념 갱신 — 무엇이 최신인지 모른다

어제는 "3 July"라 했고 오늘 "11 August"라 하면? 로그 더미에선 둘 다 검색되고 모델이 알아서 고르길 빈다. 갱신 이력이 구조여야 한다.

Kumiho의 답

저장 시점에 타입 그래프를 짓고(write-time ontology), 리콜 시점에 구조를 탄다 (structure-aware recall). 셋 다 아래에서 실데이터로 보인다.

05

저장 · 1모든 기억에는 주소가 있다 — kref 해부

kref는 Kumiho의 URI다. 프로젝트/스페이스/아이템/종류/리비전이 주소 하나에 담긴다.

kref://locomo-c26-p41facts/personal/locomo-conv-26/caroline-shares-her-transgender-journey-….conversation?r=1
        └─ 프로젝트            └─ 스페이스 (경로형)        └─ 아이템 슬러그 (내용 기반 아이덴티티)      └─ kind   └─ 리비전 번호
  • 스페이스가 타입을 인코딩: 대화는 personal/…, 사실은 facts/, 결정은 decisions/ — 조회·격리·정리가 경로 연산이 된다.
  • 슬러그 = 아이덴티티: 같은 주제를 다시 배우면 새 노드가 아니라 같은 아이템에 리비전이 쌓인다 (get-or-create).
  • ?r=N = 시간축: 모든 기억이 코드처럼 버저닝된다. 최신이 head, 역사는 한 홉 뒤.
06

저장 · 2파이프라인 — 대화에서 그래프까지

대화 턴→ Redis 작업기억 (세션 버퍼)→ 임계치 → Consolidation
LLM 1콜 · 스키마 강제 구조화 출력→ 대화 리비전 저장
+ 서버측 임베딩→ 온톨로지 분해
타입 노드 + 엣지 (결정론적)
  • 통합은 LLM 1콜 — JSON 스키마가 강제되므로 (structured output) 출력이 파싱 실패할 수 없다.
  • 스키마는 온톨로지 스위치와 무관하게 바이트 동일 — 분해를 켜도 기본 요약 품질이 변하지 않는다 (테스트로 보증).
  • 분해는 요약 JSON에서 결정론적으로 그래프를 짓는다 — 추가 LLM 콜 0회, 환각 엣지 0개.
07

저장 · 3실제 저장된 대화 리비전 LIVE DATA

지금 서버에 있는 LoCoMo conv-26의 리비전 하나를 Neo4j에서 그대로 읽었다 (요약 발췌).

# kref://locomo-c26-p41facts/personal/locomo-conv-26/caroline-shares-her-transgender-journey-….conversation?r=1
schema        : kumiho.agent_memory.v1
title         : Caroline shares her transgender journey at a school event
summary       : On 9 June 2023, Caroline recounted her experience at a school event where she
                spoke about her transgender journey and advocated for increased involvement…
facts         : Caroline started transitioning three years ago; Caroline spoke about her
                journey at a school event on 9 June 2023; Caroline has known her friends for 4 years…
events        : [one week before 9 June 2023] Caroline spoke about her transgender journey…;
                [4 years ago] Caroline moved from her home country and formed a s…
entities      : Caroline, Melanie
topics        : LGBTQ advocacy, support systems, family
event_date    : 2019-06                     # 시간 질의 랭킹에 쓰이는 valid-time
implications  : Caroline organizes a series of educational workshops…  # 미래 연결용 추론
message_count : 23        session_id : personal:user-0e90700f10:20260709:221
embedding     : [1536-dim vector]            # 서버가 title+summary로 생성·저장
tag_history   : summarized → published        # 라이프사이클이 태그로 기록됨

요약(summary)만이 아니라 facts / events / entities / topics / implications / event_date가 구조화 필드로 함께 저장된다 — 리콜 시점에 각각 다른 용도로 쓰인다.

08

저장 · 4리비전 스태킹 — 기억은 덮어쓰지 않고 쌓인다 LIVE DATA

# 위 대화 아이템의 실제 상태:
kref://…/caroline-shares-her-transgender-journey-….conversation   → 리비전 19개 스택
  • conv-26의 세션들이 통합될 때마다 같은 아이템에 ?r=1 … ?r=19로 쌓였다 — 아이템은 "주제", 리비전은 "그 주제에 대해 그때 안 것".
  • 리콜은 기본적으로 head(최신)를 보고, sibling 리비전들은 질문과의 관련도로 선별되어 컨텍스트에 합류한다 (하이브리드 코사인+LLM 랭킹).
  • 덮어쓰기가 없으므로 "그때 뭐라고 했었지?"가 언제나 답 가능 — get_revision_as_of로 시점 조회.

저장 · 5온톨로지 분해 — 한 대화가 만든 타입 노드 원장 LIVE DATA

conv-26 대화 하나(세션 19개 분량)를 온톨로지 모드로 저장한 실제 결과:

kind개수스페이스내용물
fact103/facts원자적 주장 + certainty — "answer-shaped" 단위
event77/events사건 + when + participants
entity15/entities순수 앵커 (display_name만 — 내용 없음, 연결이 존재 이유)
question10/questions미해결 질문
action / decision8 / 8/actions /decisions할 일 · 결정+이유

타입 노드도 각각 임베딩을 가진 1급 리비전이다 — 시맨틱으로 직접 검색되고(리콜 §17), kref로 직접 접근되며, 같은 주장이 재등장하면 리비전이 쌓인다.

저장 · 6실제 fact 노드와 ABOUT 클러스터 LIVE DATA

kref://locomo-c26-p41facts/facts/becoming-nicole-by-amy-ellis-nutt-inspi-05578a27.fact?r=1
  claim = "'Becoming Nicole' by Amy Ellis Nutt inspired Caroline"
  ──ABOUT──▶ …/entities/caroline.entity?r=1

kref://locomo-c26-p41facts/facts/caroline-and-melanie-attended-a-pride-f-587bdd8b.fact?r=1
  claim = "Caroline and Melanie attended a Pride fest together last year."
  ──ABOUT──▶ …/entities/caroline.entity   ──ABOUT──▶ …/entities/melanie.entity   # 두 앵커에 동시 연결
  • ABOUT 연결은 토큰 경계 매칭으로 결정 — 부분 문자열 오탐이 없다 ("AI"가 "plan finalized"에 안 붙음, 한글 "김"이 "김치"에 안 붙음).
  • 한 fact가 여러 엔티티에 연결되면 그 fact는 나중에 브리지 조인의 후보 증거가 된다 (§16).

저장 · 7엣지 시스템 — conv-26 한 대화의 실측 그래프 LIVE DATA

엣지실측 개수의미생성 규칙 (전부 결정론적 — LLM 추측 없음)
DERIVED_FROM208출처: 타입 노드 → 원본 대화materialization 시 항상
ABOUT175fact/decision → 언급된 엔티티토큰 경계 멘션 매칭 (Hangul-aware)
INVOLVES89event → 참여 엔티티participants 필드에서 직접
SUPERSEDES29신념 갱신: 새 주장 → 대체된 옛 주장같은 주제 후보 검색 + 토큰 중첩 Jaccard ≥ 0.6
DEPENDS_ON0*결정 → 근거 fact같은 통합 내 fact와 중첩 ≥ 0.4 (이 대화에선 임계 미달)

* 임계치를 넘는 근거 결합이 없으면 엣지를 만들지 않는다 — 불확실하면 연결하지 않는 것도 설계다. 총합: 대화 1개 → 노드 221개 + 엣지 501개, 추가 LLM 비용 0.

저장 · 8SUPERSEDES — 신념 갱신이 구조가 되는 순간 LIVE DATA

13

저장 · 9인덱스 위생 — 구조가 검색을 오염시키지 않게

타입 노드 텍스트는 대화의 복제라, 렉시컬 인덱스에 넣으면 코퍼스 전체의 BM25 IDF가 뒤틀린다. 그래서:

// Kumiho Server (Rust) — 파생 kind는 풀텍스트 코퍼스에서 제외
pub const FULLTEXT_EXCLUDED_KINDS: &[&str] =
    &["entity", "fact", "decision", "event", "action", "question"];
  • 타입 노드는 렉시컬 검색에서 투명 (이름/kind 필드만 남김) — IDF 오염 실측 −0.031을 제거.
  • 대신 벡터 검색과 kref 그래프 순회로는 완전히 도달 가능 — 정확히 의도된 분업: 구조는 그래프로, 어휘는 대화로.
  • 레거시 데이터용 idempotent 백필이 옛 오염 블롭을 정리한다.

리콜 · 1리콜 파이프라인 — 7단계

① 리포뮬레이션
질문→N개 각도→ ② 하이브리드 병렬 리콜
각도별 BM25+벡터→ ③ 구조 순회
엣지 따라가기→ ④ 브리지 조인
그래프 JOIN→ ⑤ fact 레그
타입 주장 직접 검색→ ⑥ 재랭크
증거·시간·다양성→ ⑦ 추가-비대체 조립
additive compose

④⑤⑦(초록)이 타입 그래프가 만드는 차별점이다. 온톨로지를 끄면 ①②③⑥만 남고 출력은 기존 파이프라인과 바이트 동일 — 구조는 순수하게 더해지기만 한다.

15

리콜 · 2하이브리드 검색 — 서버측 융합

  • 레그 3종: 아이템 풀텍스트(이름·kind·메타 블롭) + 리비전 풀텍스트 + 리비전 벡터(1536-dim 코사인).
  • 각 레그 점수를 레그별 정규화 후 가중 합산 — BM25의 무한 스케일이 0..1 코사인을 짓누르던 고전적 실패를 제거. 여러 레그가 동의하면 가산점.
  • 퍼지 질의(getting~1 pet~1, 편집거리 1)로 오타 내성; 한국어는 ko-dic 형태소 토크나이저로 인덱싱.
  • 임베딩 생성이 느리면 5초 타임아웃 후 풀텍스트-온리로 우아하게 강등 — 검색은 절대 죽지 않는다.
16

리콜 · 3엔티티-브리지 조인 — 그래프가 하는 JOIN LIVE DATA

멀티홉 질문 = 각도들의 교집합. 서로 다른 각도의 상위 히트가 같은 엔티티를 ABOUT으로 가리키면 그 엔티티가 브리지고, 브리지의 fact들이 연결 증거다.

conv-26 실측 앵커in-degree판정
entities/caroline.entity149허브 — defer (모든 각도가 도달 → 조인 판별력 없음, 후순위로만)
entities/melanie.entity82허브 — defer
entities/youth-center.entity4판별 브리지 — 우선 채택
  • 브리지의 fact 노드는 실제 상속 점수(0.9 × 약한 각도의 점수)를 받는다 — 양쪽 각도가 보증한 관련성이므로 1급 히트로 경쟁.
  • 허브는 버리지 않고 미룬다(defer) — 2인 대화에선 화자가 곧 조인 키이기 때문. 판별 브리지가 예산을 못 채울 때만 허브 사용.
17

리콜 · 4fact-recall 레그 — 정답 모양의 단위를 직접 가져오기

  • 원 질문으로 facts 스페이스를 1회 시맨틱 검색 — fact는 "Caroline is researching adoption agencies…"처럼 정답과 같은 모양의 원자 주장이라, 한 개의 히트가 곧 답이 된다.
  • 인덱스 위생(§13) 덕에 이 도달은 벡터-순수 — 렉시컬 오염 없이 시맨틱으로만 닿는다.
  • 점수는 가장 약한 대화 히트 × 0.9 (축-불변 상대점수) — 크로스인코더가 점수 축을 바꿔도 fact가 대화를 앞지르거나 밀어낼 수 없다. 더하기만 가능한 설계.
  • 실측 (같은 코퍼스 199문항 페어): 4카테고리 +0.054, 5개 카테고리 전부 상승, 문항별 23승 172무 4패.

리콜 · 6추가-비대체 조립 — 구조는 점수를 깎을 수 없다

# 컨텍스트 슬롯 (top_k=5 예시)
[1..5]  평면 리콜의 top-K 그대로            # 역사적 head-slice, 단 한 슬롯도 대체 금지
[+1,+2] 브리지 fact (실점수, 자체 예산)      # 그래프 JOIN 증거
[+1,+2] fact-recall 주장 (자체 예산)         # 정답 모양 단위
  • 기반 컨텍스트는 온톨로지 OFF와 바이트 동일 — 구조 증거는 언제나 위에 얹힌다.
  • 그래서 회귀가 구조적으로 불가능하고, 실측도 그렇다: 199문항 페어에서 나빠진 문항 4개 vs 좋아진 문항 23개.
  • 이 원칙은 재랭크·트림·조립 3단계 전부에 일관 적용된다 (예산 미러링).

증거 · 2측정 방법론 — 페어 A/B가 아니면 믿지 않는다

  • 같은 코퍼스, 같은 질문, 변수 하나: 인제스트를 고정하고 answer-only 재평가로 읽기 경로만 A/B — LLM 비결정성 노이즈(단일 대화 기준 ±0.05)를 원천 차단.
  • 단일 런 델타로는 어떤 코드도 판정하지 않는다 — 대화 단위 슬라이스는 런마다 흔들리는 게 정상이다.
  • 공개 수치는 full-suite(1,986문항)에서만 — 큰 n에서 분산이 죽는다. 다만 재현되는 것은 메모리/리콜 레이어와 고정 모델 수치(0.531)이지, 드리프트하는 모델 위의 날짜 간 절대 점수가 아니다. 동일 컨텍스트를 이후 gpt-4o 스냅샷으로 재답변하면 −0.056까지 내려간다 — 그래서 답변 모델을 gpt-4o-2024-08-06로 고정하고 응답마다 system_fingerprint를 남긴다.
  • 유료 런은 1문항 프리플라이트(측정 대상 기능의 발화 로그 확인) 후에만 발사.
